Policywright's design rule: **the synthesizer configures stock OpenZeppelin
policies before ever generating fresh Rust.** New policy code is generated only
where no stock policy can express the constraint. This is the permanent
default, not a v0 shortcut. The stock building block configured today is
`spending_limit`; the stock threshold policies — `simple_threshold` and
`weighted_threshold` — are Planned composition targets for multi-signer flows
(see [Planned](#planned)).

Full decision table, live artifacts, and harness proof:
[docs/compose-vs-generate.md](https://github.com/kunal-drall/policywright/blob/main/docs/compose-vs-generate.md)
(D2.4).

## Why compose-first is the default permanently

Generated authorization code guards user funds, and every freshly generated
line is a line nobody has reviewed yet:

- **Stock policies carry their review with them.** OpenZeppelin's building
  blocks are shared, maintained code. Configuring them means the enforcement
  logic executing on-chain is the same code everyone else runs and scrutinises
  — only the parameters are new, and parameters are auditable at a glance.
- **Fresh codegen multiplies audit surface.** A generator that emits a new
  contract per delegation produces code no audit has covered. Keeping
  generation as the rare fallback keeps the unaudited surface small and
  reviewable.
- **Parameters are legible to reviewers and wallets.** "Stock `spending_limit`,
  cap 1.1 native XLM per 24 h" is a statement a wallet, an agent, or a human can
  check mechanically. Arbitrary generated code is not.

For those reasons the ordering is not a maturity phase to grow out of: even
with a hardened generator, composing stock policies stays the first choice, and
generation stays the fallback.

## What ships today (D2.4)

- **Compose:** the live claim→swap recording emits installable stock
  `spending_limit` params on the native-XLM transfer rule
  ([`examples/live/context-rule.json`](https://github.com/kunal-drall/policywright/blob/main/examples/live/context-rule.json)),
  citing OZ `spending_limit.rs:88-94`. Caps the stock policy cannot express
  become DELTA notes — never rejectable install shapes.
- **Generate:** call frequency has no stock counterpart, so it is emitted as
  `FrequencyLimitPolicy`
  ([`contracts/frequency-limit-policy`](https://github.com/kunal-drall/policywright/blob/main/contracts/frequency-limit-policy)),
  stamped `ILLUSTRATIVE / UNAUDITED — NOT DEPLOY-READY`, with storage segregated
  by `(smart_account, context_rule_id)`.
- **Harness:** permit original / deny over-cap (composed) / deny
  repeat-within-window (generated) on the live sequence —
  [`simulation-report-compose-and-generate.md`](https://github.com/kunal-drall/policywright/blob/main/examples/live/simulation-report-compose-and-generate.md).
- **Boundary tests:**
  [`test/compose-boundary.test.ts`](https://github.com/kunal-drall/policywright/blob/main/test/compose-boundary.test.ts).

## Planned

Composition of the stock threshold policies — `simple_threshold` and
`weighted_threshold` — is planned for when multi-signer flows enter the
synthesizer's scope; v0's worked example is a single-signer flow and does not
exercise them. See the [Roadmap](/roadmap/).
